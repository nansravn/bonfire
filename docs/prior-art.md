The field splits into three buckets. **Discord-triggered hobby bots** (nichogx, the three R11 bots) are single always-on Node/Python processes that poll one game's player count and shell out to one cloud provider's start/stop API — no IaC, usually unmaintained within a year or two, and none guard against a player-count query failing silently. **Proxy/wrapper tools** (lazymc, minecraft-server-hibernation, infrared) solve a narrower problem well — waking a local Minecraft *process* on the first TCP connection — but that mechanism is Minecraft-specific and doesn't reach a game behind a fully deallocated cloud VM. **Platform-scale tooling** (Pterodactyl, Crafty, LinuxGSM, AMP, Agones, PlayFab MPS, the Azure/AWS scheduler solutions) is either always-on management with no idle-shutdown at all, or schedule-based rather than usage-based. Only Hyveon (ex-`game-server-deploy`) combines a serverless Discord bot with automatic shutdown, and it targets AWS with a traffic heuristic rather than a real player count. Three gaps recur across the whole set and are exactly what Bonfire fills: nothing here targets **Azure**; almost everything is a **persistent bot process** rather than a serverless Discord Interactions Endpoint; and no project shuts down on an actual **player count with an "unknown never extinguishes" safety rule** — they either use a schedule, a traffic/packet proxy for "activity", or trust a player-count query that silently fails closed (extinguishes) or open (never extinguishes) instead of alerting.

## Patterns from the closest projects

For each pattern: where it lives in the source, what it does, and whether Bonfire copies, adapts, or avoids it.

### nichogx/game-servers-manager-bot

- **Start → wait-for-ready → post-address loop** — [`src/managerbot.ts`](https://github.com/nichogx/game-servers-manager-bot/blob/master/src/managerbot.ts), functions `notifyInstanceStarting` and `notifyServerStarting`. After `startInstance()`, it recursively re-checks the EC2 instance state every 8 s until `State.Code === 16` (running), edits the Discord status message, then recursively polls the Minecraft ping every 20 s until it answers, and edits the message again with an embed of IP, port and player list. Bonfire **adapts** this shape: `/bonfire ignite` replies immediately and a follow-up post fires when the adapter's `is_ready` succeeds (prd.md §7.1, §7.6), but the poll itself moves from the bot process to the on-VM agent, and the fixed 8 s/20 s literals become the configurable `idle_check_interval`.
- **Player-count poll and its interval** — [`src/ServerManagers/ServerManager.ts`](https://github.com/nichogx/game-servers-manager-bot/blob/master/src/ServerManagers/ServerManager.ts) wires an `IntervalManager` to `checkShouldClose()` at `checkIntervalMinutes * 60` seconds; [`config.example.json`](https://github.com/nichogx/game-servers-manager-bot/blob/master/config.example.json) defaults `check_every_x_minutes` to 15. Bonfire **adapts** the idea of a fixed poll cadence but lowers it: PRD §6.7 sets `idle_check_interval = 1` minute, justified by the A2S query being local and cheap (prd.md §6.7), versus this bot's SSH/API round-trip to AWS.
- **How it decides "empty"** — [`src/ServerManagers/MinecraftServerManager.ts`](https://github.com/nichogx/game-servers-manager-bot/blob/master/src/ServerManagers/MinecraftServerManager.ts), `checkShouldClose()`: `result.players.online === 0` closes the server, and — notably — any error from the player-count query (`.catch`) is treated as "can't access server, assuming dead, shutting down." Bonfire **avoids** this fail-closed behavior on purpose: PRD §7.6 and §12 make `unknown` a distinct outcome from `0`, and the safety rule is that the watchdog never extinguishes on `unknown` (the opposite of this bot's catch-block).

### CoderCoco/game-server-deploy → Hyveon

- **Lambda handler for the Interactions Endpoint** — [`app/packages/lambda/interactions/src/handler.ts`](https://github.com/CoderCoco-Studios/Hyveon/blob/main/app/packages/lambda/interactions/src/handler.ts). Every request is verified with `@noble/ed25519`'s `verifyAsync` against the raw, unparsed body (`timestamp + rawBody`) before anything else runs, returning 401 on failure or on a missing public key. A slash command gets an immediate deferred ack (`type: 5`, `RESPONSE_DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE`), and the actual ECS work is handed off by async-invoking a second Lambda (`InvocationType: 'Event'`) so the handler replies inside Discord's 3-second budget regardless of AWS latency. The edit itself happens in [`app/packages/lambda/followup/src/handler.ts`](https://github.com/CoderCoco-Studios/Hyveon/blob/main/app/packages/lambda/followup/src/handler.ts), which `PATCH`es `/webhooks/{application_id}/{interaction_token}/messages/@original` (up to Discord's 15-minute window) using only the interaction token — no bot token needed. Bonfire **copies** this exact shape: prd.md §6.3 names the same pattern (validate signature, act), and §7.1's "reply immediately, post the real result later" behavior is the same split across the Function's synchronous ack and its asynchronous follow-up post.
- **The Terraform layout** — as R8 describes it (and as the PRD's §6.3 comparison assumes), the project originally provisioned everything with Terraform. That is no longer true of the current source: an [`openspec` change record](https://github.com/CoderCoco-Studios/Hyveon/blob/main/openspec/changes/archive/2026-08-10-migrate-iac-to-pulumi/proposal.md) shows the IaC was migrated to Pulumi (TypeScript, Automation API, invoked from inside the packaged Electron app rather than a host-installed CLI) on 2026-08-10, and no `terraform` directory remains in the repo. The current layout lives under [`app/packages/infra/src`](https://github.com/CoderCoco-Studios/Hyveon/tree/main/app/packages/infra/src) — one file per AWS concern (`network.ts`, `ecs.ts`, `iam.ts`, `route53.ts`, `secrets.ts`, `lambdas.ts`), composed by `program.ts`. Bonfire **adapts** the *shape* (one module per concern under `infra/modules/`, prd.md §6.6) but keeps Terraform rather than following this project's move to Pulumi, since prd.md §6.6 predates and doesn't reflect this migration.
- **The traffic-based watchdog, and why Bonfire avoids it** — [`app/packages/lambda/watchdog/src/handler.ts`](https://github.com/CoderCoco-Studios/Hyveon/blob/main/app/packages/lambda/watchdog/src/handler.ts). On an EventBridge schedule, it reads CloudWatch `NetworkPacketsIn` on each running task's ENI over a `CHECK_WINDOW_MINUTES` window (default 15), compares against `MIN_PACKETS` (default 100), and stops the task after `IDLE_CHECKS` (default 4) consecutive idle windows — 60 minutes by default. Games can opt out of the packet heuristic into a declared per-game health check instead, but both verdict sources are still deliberately **fail-active** (a CloudWatch query error or a health-check invocation failure is treated as "active", never as "idle"). Bonfire **avoids** the packet-count signal itself: a quiet-but-populated game (or a keepalive-only client) can read as idle to a packet threshold, and a noisy-but-empty one can read as active, neither of which a raw byte/packet count can tell apart. PRD §7.6 and §6.4 instead call the adapter's own `player_count` (an actual game-protocol query), and explicitly add the three-way outcome (`0` / `>0` / `unknown`) that this project's fail-active packet and health-check paths approximate but never name as a distinct state.

### timvisee/lazymc

- **The per-server config shape and the sleep/wake state machine** — [`src/config.rs`](https://github.com/timvisee/lazymc/blob/master/src/config.rs) defines one `Config` struct per proxied server, loaded from a single `lazymc.toml` (sections: `public`, `server`, `time`, `motd`, `join`, …). The state machine itself lives in [`src/server.rs`](https://github.com/timvisee/lazymc/blob/master/src/server.rs): a 4-value `enum State { Stopped, Starting, Started, Stopping }`, driven by [`src/monitor.rs`](https://github.com/timvisee/lazymc/blob/master/src/monitor.rs)'s `monitor_server` loop, which polls server status every 2 s and calls `should_sleep()` — true only when `State::Started`, no players are online, no `keep_online_until` grace period is active, and `last_active` has exceeded `config.time.sleep_after`. Bonfire **adapts** the small, named-state model (its own states are `lit`/`igniting`/`extinguishing`/`out`, prd.md §7.1) and, more directly, the "grace period that cancels a pending shutdown" idea reappears as the v1.5 "keep it lit" button (prd.md §7.3).
- **What its adapter-like boundary looks like** — lazymc's unit of control is one OS process per config block: it spawns the Minecraft server directly (or proxies to an already-running one) and supervises it with `start`/`stop`/`force_kill`, all within `server.rs`. There's no notion of a swappable, game-declared contract beyond that — the proxy itself hardcodes the Minecraft handshake protocol. Bonfire's adapter interface (prd.md §7.6: `install`/`start`/`stop`/`is_ready`/`player_count`/`health`/`backup`, one directory per game under `games/<name>/`) is a broader, game-agnostic contract that lazymc doesn't need because it only ever speaks one protocol.
- **Why wake-on-connect does not transfer to a UDP game behind a deallocated VM** — lazymc and infrared both work by intercepting the *TCP* handshake, holding or queuing the client while the real server boots, because Minecraft's protocol is TCP and the "server" being woken is already a process on an already-running host. Neither condition holds for Bonfire: Valheim's player traffic and its A2S status query are UDP (prd.md §7.6), which has no handshake to hold open and no reliable-delivery guarantee to buffer against, and the thing being "woken" is a fully deallocated VM (~2 minutes to become reachable at all, prd.md §8), not a process on a warm host. A transparent proxy in front of a UDP port pointing at a deallocated VM has nothing to intercept — Bonfire's "ignite" is necessarily an explicit, out-of-band Discord command rather than a wake-on-first-packet proxy.
